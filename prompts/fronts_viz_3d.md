## Primary script

We will generate a primary script in fronts/scripts/fronts_viz_3d.py that will:

- Input a 3D density field file. For now, we will restrict to a single tile generated by the generate_tile script in llc4320-native-grid-preprocessing.
- The user will provide a labeled fronts file which contains the fronts labeled as integers.
- The user will provide i,j or lat,lon coordinates for the fronts.  You will use this to find the front in the labeled fronts file.
- The code will generate a 3D view of the selected front to depth.  The coloring will indicate the density field.  The view will be a 3D plot with the x,y-axes being the i,j coordinates and the z-axis being the depth
- The figure should go to several layers below the mixed layer depth, defined as the depth where the density is 0.125 kg m^-3 greater than the potential density at 10m below the surface.
- If possible, the user should be able to change the perspective of their view
- If possible, the user should be able to save the figure to a file.
- If possible, the user should be able to modify the contrast

1. `parse_args()` — CLI:
    - `--density-tile PATH` (required), `--labels PATH` (required)
    - locator: `--i INT --j INT` (rect grid) **or** `--lat FLOAT --lon FLOAT` — exactly one of the two pairs
    - `--output PATH.png` (required), `--interactive-html PATH.html` (default: derived from `--output`)
    - `--mode {isopycnals,volume}` (default `isopycnals`)
    - `--isopycnals FLOAT [FLOAT ...]` (default: auto-pick 5 levels evenly spaced between the 5th/95th percentile of surface sigma0 in the cropped bbox, excluding the front itself — printed to stdout for pinning)
    - `--opacity {sigmoid,linear,geom}` (default `sigmoid`, only used in `volume` mode)
    - `--clim LO HI` (sigma0 colour limits; default: data 2%–98% percentiles)
    - `--cmap-volume STR` (default `viridis`), `--cmap-curtain STR` (default `magma`)
    - `--zscale FLOAT` (default `50.0`)
    - `--margin INT` (default `50` pixels around the front bbox)
    - `--n-below INT` (default `3` Z-levels below `max(k_mld)` in the bbox)
    - `--cpos JSON` (optional camera triple to lock framing), `--show` (open an interactive window instead of off-screen)
    - `--no-inset` (skip the 2D matplotlib companion); `--inset-output PATH.png` to override the default `{stem}_inset.png`
2. `pick_front_label(labels_tile, locator, XC_rect, YC_rect)` — return the integer label at the requested location.
    - If `(i, j)`: convert to tile-local rect indices via `rect_i_start`, `rect_j_start`, then `labels_tile[j_local, i_local]`. Error if 0.
    - If `(lat, lon)`: compute the nearest pixel in the tile by `argmin((XC_rect - lon)^2 + (YC_rect - lat)^2)`, then **snap** to the nearest non-zero label pixel within the tile window using a small BFS / `scipy.ndimage.distance_transform_edt` style lookup. Error if no labelled pixel exists inside the tile.
3. `remap_to_rect(arr_face, j_lookup, i_lookup)` — fancy-index `arr_face[..., j_lookup, i_lookup]` to put any face-local 2D/3D array onto tile-local rect axes (the same pattern as [dev/mld/plot_isopycnals.py](../../fronts/dev/mld/plot_isopycnals.py)). Apply to `sigma0` and `XC`/`YC` so everything downstream shares the rect frame.
4. `mixed_layer_depth_field(sigma0_rect, Z)` — **lives in the new module [fronts/llc/analysis.py](../fronts/llc/analysis.py)**. Vectorised 2D MLD using the 0.125 rule (lifted from [dev/mld/plot_top_N_density_profiles.py](../../fronts/dev/mld/plot_top_N_density_profiles.py); the scalar `mixed_layer_depth` also moves there, and the old file is refactored to import them). Returns `(z_mld(j,i), k_mld(j,i))`, NaN where the column never reaches the threshold.
5. `front_bbox_and_crop(labels_tile, selected_label, margin)` — `np.where(labels_tile == selected_label)` to get the bbox; pad by `margin`, clip to tile bounds. Returns `(j_slice, i_slice)` to apply to the rect-frame arrays. (Avoids needing `front_index.parquet`.)
6. `truncate_depth(sigma0_rect_cropped, Z, k_mld_cropped, n_below)` — pick `k_clip = min(K-1, np.nanmax(k_mld_cropped) + n_below)`; return `sigma0[:k_clip+1]` and `Z[:k_clip+1]`.
7. `build_pyvista_grid(sigma0_cropped_clipped, Z_clipped, zscale)` — wrap as `pv.RectilinearGrid(x=i_axis, y=j_axis, z=Z_clipped * zscale)` (axes in **POINT** counts, see patterns_reference §2). Stamp `grid["sigma0"] = field.ravel(order="F")` — Fortran order is the documented silent-bug trap.
8. `build_front_curtain(front_mask_cropped, sigma0_rect_cropped_clipped, Z_clipped, zscale)` — implementation (b) from round 1, **with branching support**:
    - Run `skimage.morphology.skeletonize` (idempotent on already-thinned masks) then `skan.csr.Skeleton` (or a small custom DFS on the 8-neighbour adjacency) to decompose the front into a list of simple branches between endpoints/junctions.
    - For **each** branch, build a `pv.StructuredGrid` ribbon (horizontal = branch polyline, vertical = `Z_clipped * zscale`). Sample `sigma0` along each ribbon via `scipy.ndimage.map_coordinates` and stamp as `curtain["sigma0"]`.
    - Return a `pv.MultiBlock` of all ribbons; the renderer iterates over them so every branch is drawn.
9. `pick_isopycnals_across_front(sigma0_rect_cropped_clipped, front_mask_cropped, user_levels)` — **lives in `fronts/viz/fronts_3d.py`**:
    - If `--isopycnals` given, return those.
    - Else: select a near-surface reference slice (k where `|Z|` is nearest 10 m, matching the MLD convention). Mask out the front pixels (and a 1-pixel dilation buffer) from that slice. Take `sigma_low = nanpercentile(sigma_surface, 5)` and `sigma_high = nanpercentile(sigma_surface, 95)` — these approximate the "warm" and "cold" sides of the front. Return `np.linspace(sigma_low, sigma_high, 5)`.
    - **Print** the chosen levels to stdout so the user can pin them with `--isopycnals ...` on the next run.
10. `render_3d(grid, curtain_multiblock, levels, mode, clim, cmaps, opacity, cpos)` — lives in `fronts/viz/fronts_3d.py`; orchestrates the scene using [fronts/viz/pv_helpers.py](../fronts/viz/pv_helpers.py):
    - `ensure_display()` (Xvfb for headless), `new_plotter(theme=scientific_theme())`.
    - Mode (b) **isopycnals**: `iso = grid.contour(levels, scalars="sigma0")`; `add_scalar_field(pl, iso, "sigma0", label="σ₀", units="kg m⁻³", cmap=cmap_volume, clim=clim, opacity=0.6)`.
    - Mode (a) **volume**: `pl.add_volume(grid, scalars="sigma0", cmap=cmap_volume, clim=clim, opacity=opacity)`.
    - Curtain (both modes): iterate over the MultiBlock branches and `add_scalar_field(pl, ribbon, "sigma0", label="σ₀ on front", units="kg m⁻³", cmap=cmap_curtain, clim=clim)`. Only the first branch contributes a scalar bar (`show_scalar_bar=False` on the rest) so the legend isn't duplicated.
    - Axes: `pl.show_bounds(xtitle="i (rect)", ytitle="j (rect)", ztitle=f"depth × {zscale:.0f} [m]")`. **No** lon/lat text in the 3D scene — lon/lat goes on the companion 2D inset.
11. `plot_bbox_inset(surface_sigma0, front_mask, XC_rect, YC_rect, ...)` — **lives in [fronts/viz/viz_utils.py](../fronts/viz/viz_utils.py)** (extend the existing module). ### PyVista — pros and cons

**Pros**
- Native support for non-uniform vertical grids: `pv.RectilinearGrid` handles the LLC4320 Z-levels (geometric spacing from ~1 m near the surface to hundreds of m deep) without resampling.
- Volume rendering plus isosurfaces both available, so the same data can be shown as a continuous gradient *and* picked level sets (patterns_reference section 5).
- The repo already ships [pv_helpers.py](../fronts/viz/pv_helpers.py): scientific theme, off-screen Xvfb handling, scalar-bar formatting, PNG + interactive-HTML export — nothing new to build.
- Reproducible cameras: `save_figure` returns the camera triple and accepts it back, satisfying the "user can change perspective" requirement and locking framing across runs.
- Interactive rotation via `export_interactive` (trame) gives the user a real 3D explorer in a browser — better than matplotlib's 3D for that goal.
- Colormap + clim controls map cleanly to the `--clim` "contrast" requirement.
- Headless-safe: critical because this will be run on the same boxes that produced the V4 fronts.

**Cons**
- VTK is a heavyweight dependency; first install is slow and image-size large.
- True volume rendering needs the `pyvista[jupyter]` (trame) extras for HTML export; if those are missing we degrade to PNG only.
- Off-screen on Linux needs Xvfb (already handled by `pv_helpers.ensure_display`, but it's a runtime requirement).
- Aspect ratio is not automatic: depth ~1500 m versus 720 pixels × ~2 km horizontal = ~1500 km — without a Z exaggeration factor everything collapses to a thin sheet. We expose `--zscale` (default ~50–100x) to compensate.
- Polishing for publication (titles, multi-panel composition, annotations) is less ergonomic than matplotlib; a small matplotlib companion figure may still be wanted.
- Volume opacity transfer functions are easy to misuse — structure can hide in the alpha channel. We'll start with isosurfaces + a coloured curtain and only switch to volume rendering on request.

#### Colormap suggestions (denser water = darker)

`viridis` (the default) maps higher σ₀ to *lighter* (yellow), which is backwards if you want "dense = dark." Options where denser water is darker, all accepted by the `--cmap-volume` CLI flag:

| Colormap | Family | Notes |
|---|---|---|
| `dense` | cmocean | Purpose-built for ocean density. Cream → dark purple. Perceptually uniform. **Recommended default for σ₀.** |
| `deep` | cmocean | Light yellow → deep blue. Perceptually uniform; reads as "depth/density." |
| `gray` | cmocean | Perceptually-uniform monochrome. White → black. Good for grayscale print. |
| `Blues` | matplotlib | Light blue → dark blue. Familiar, single-hue. |
| `bone` | matplotlib | Bluish-white → black. Classic publication look. |
| `viridis_r` | matplotlib | Reversed viridis: yellow → dark purple. Keeps viridis's perceptual properties. |
| `cividis_r` | matplotlib | Reversed cividis; colorblind-safe. |
| `magma_r` / `plasma_r` / `inferno_r` | matplotlib | Reversed sequential, dark = high. |
| `Greys` / `gray_r` | matplotlib | Pure grayscale, light → dark. |

PyVista's `get_cmap_safe` accepts the bare cmocean names (`dense`, `deep`, `gray`) — not `cmo.dense`. Example: `--cmap-volume dense`.

A re-run of the California Current example with `--cmap-volume dense` confirms the change: the right edge of the bbox (denser deep water) now reads as dark purple, the top (lighter surface water) as cream/yellow, with the orange front iso-surface still standing out against this background.

#### Why the 3-D font sizes looked "fixed and small"

The fonts weren't truly fixed — `render_3d` has always exposed `font_size`, `title_font_size`, and `label_font_size` parameters. But the **script** was hardcoding their values at the call site (or letting `render_3d` use its baked-in defaults), so from the CLI's point of view they were not configurable. Two compounding factors made them look small:

1. **PyVista doesn't auto-scale fonts with the rendered image size.** The off-screen window size set by `pv_helpers.new_plotter` is `(1600, 1200)` and the screenshot is supersampled at `scale=2`, so the final PNG is `3200 x 2400`. A "font size 20" rendered at 14 px ends up as ~14 px in the 1600-wide window, then is supersampled to ~28 px in the 3200-wide PNG — small relative to the bbox.
2. **The camera framing was wider than the bbox**, leaving a lot of whitespace around the volume, so labels at the bbox edges occupied a smaller fraction of the image than expected.

The fix in v1.6 is to (a) raise the **default** font sizes inside `render_3d` (now 56 / 60 / 44), and (b) expose them as CLI overrides so the user can dial up further without editing source:

```
--font-size INT          override bounds-axis font size (default 56)
--title-font-size INT    override scalar-bar title font size (default 60)
--label-font-size INT    override scalar-bar tick label font size (default 44)
```

The script only forwards each value to `render_3d` when the user supplies it, otherwise the renderer's baked-in defaults apply — so the CLI defaults match the v1.6 baked-in defaults but can still be tuned per-run.

The combined effect is a bar that's noticeably wider, taller, and shifted left enough that its title (rendered to the right of the bar in vertical mode) doesn't run off the right viewport edge. `position_y` was lowered from 0.55 → 0.30 because the bar-top-plus-title text was clipping above the top of the viewport at 60 pt title font; centring the bar vertically (0.30 to 0.80) leaves ~15 % of the viewport above the bar for the title.

Verified on the California Current example with `--cmap-volume dense`: the bar fills more of the right margin, the title `sigma0 (kg/m^3)` is fully readable, and tick labels (24.4 → 25) are visible at the bar's left edge.

Open items for a future round:
- The curtain-on case still uses `position_y=0.10` for its scalar bar; if `--curtain` is opted into, the two bars would overlap at the new height of 0.50. Trivially fixable by passing a smaller height when two bars are active, but not pursued because `--draw-curtain` is off by default in v1.4+.
- The CLI doesn't yet expose `--top-marker-opacity` or `--front-iso-opacity` — also low-effort follow-ups.
